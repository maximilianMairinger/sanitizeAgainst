Coverage exists. Branch test/audit-findings carries one test per finding — 88 in test/src/audit.ts, plus five compile-time gaps and the SA-32 fixture. Known-broken expectations are wrapped so CI stays green today and fails the moment a bug is fixed, which is the signal to promote the test. AUDIT_STRICT=1 npx jest audit shows the real red list: 74 failing, 14 passing. Nine gaps encode a policy choice rather than an unambiguous bug and are marked as such.

The headline. One line of code — knownInputObjects.set(input, out) running before out is populated — accounts for seven separate symptoms, including silent loss of required fields, privilege escalation through defaults, and unwanted properties surviving the filter. It is reachable through the most ordinary use of OR there is: a discriminated union.

The second theme. Validation failure is signalled by throwing, and OR/NOT/matches/soft catch everything. An attacker who can make a pattern crash — deeply nested JSON is enough — chooses which branch validates them. With OR(strictPattern, any) that is a complete sanitization bypass.

What holds. The core __proto__ defence works exactly as designed for fully-specified object patterns. Every pollution finding below comes from a hole around it — pass-through leaves, key transforms, patterns loaded from JSON — not from the guard itself. I could not write a single global Object.prototype during sanitization; that always required a downstream merge.

Critical

All three are reachable by posting JSON to an endpoint, and all three fail open — they let something through rather than rejecting it.

SA-01Critical

An aborted branch's half-built object is served as a valid result

The object-pattern matcher registers its output in the cycle cache before filling it. When a pattern aborts midway — which is exactly what every non-matching OR branch does — the abandoned, partially-populated object stays in the cache. The next branch asks the cache for the same input, gets a cache hit, and returns the wreckage of the previous attempt without validating anything.

A discriminated union is the canonical use of OR, and it is broken:

sanitize(new OR(
  { kind: new CONST("comment"), body: String },
  { kind: new CONST("like") }
))(JSON.parse('{"kind":"like"}'))

// expected  { kind: "like" }
// actual    {}                 ← required field vanished, no error

The same mechanism promotes a failed branch's defaults over the correct branch's:

sanitize(new OR(
  { isAdmin: true,  mustFail: Number },   // aborts on mustFail…
  { isAdmin: false }                      // …but its isAdmin=true survives
))(JSON.parse('{}'))

// { isAdmin: true }   ← privilege escalation from an empty request body

And it lets properties through that the matching pattern never mentioned, breaking the README's promise that extra properties are ignored:

sanitize(new OR({ a: String, b: String, c: String }, { a: String }))(JSON.parse('{"a":"x","b":"y"}'))
// { a: "x", b: "y" }   ← b is not in the pattern that matched

It is not confined to OR. Any composition where one pattern touches the input and fails before another pattern sees it hits the same cache:

// "reject this shape, then enforce that shape" — an idiomatic composition
sanitize(new AND(new NOT({ a: Number }), { b: String }))(JSON.parse('{"b":"hi"}'))
// {}                      ← every required field gone
sanitize({ b: String })(JSON.parse('{"b":"hi"}'))
// { b: "hi" }             ← control

// deep OBJECT builds `new OR(valuePattern, this)` internally, so it inherits the bug
sanitize(new OBJECT({ id: Number }, false, true))(JSON.parse('{"a":{"x":"str"}}'))
// { a: {} }               ← should have thrown; invalid data accepted as empty

sanitize(new OR(new AWAITED({ x: String }), new AWAITED({ y: Number })))(Promise.resolve({ y: 1 }))
// {}                      ← same bug across the await boundary

Objects produced this way also carry a null prototype, because the closing Object.setPrototypeOf(out, Object.prototype) is on the path that never ran. JSON.stringify still works on them, so this usually surfaces far from the sanitizer as r.toString is not a function or a failed hasOwnProperty call.

SA-02Critical

The attacker picks which branch validates them, by crashing the others

Failure is signalled by throwing, and the combinators catch every throwable — a RangeError from stack exhaustion is indistinguishable from "this pattern did not match". Since input nesting depth is attacker-controlled and recursive patterns recurse once per level, the attacker decides which patterns are allowed to run.

NOT becomes fail-open: an input the pattern genuinely matches is accepted, because the match crashed instead of completing.

const deep = n => '{"a":'.repeat(n) + '"L"' + '}'.repeat(n)
const pat  = () => new OBJECT(String, false, true)

sanitize(new NOT(pat()))(JSON.parse(deep(500)))
// throws "Matched even though it is negated."   ← correct
sanitize(new NOT(pat()))(JSON.parse(deep(4000)))
// returns the input                             ← accepted; the pattern still matches it

With OR it is a complete bypass. Add nesting until the strict branch runs out of stack, and the permissive branch takes over:

sanitize(new OR(new OBJECT(String, false, true), any))(JSON.parse(deep(4000)))
// returns the raw, unfiltered input object (=== input)

The threshold sits between depth 500 and 1500 on a default Node 22 stack, while JSON.parse itself handles 200,000 levels — so the window is wide and trivially probed. The RangeError is also laundered into Error: All patterns failed by deep OBJECT's internal OR, so nothing in the logs indicates a crash occurred.

A throwing getter is the same attack without the nesting, wherever input does not come from JSON.parse:

const input = { get role() { throw new Error("x") } }
sanitize(new NOT({ role: String }))(input) === input   // true — accepted
Root causeOR.matches, NOT.matches, matches() and OBJECT's soft mode all use bare catch. Nothing distinguishes a validation failure from a resource or programming error.

SA-03Critical

Pass-through leaves hand the caller a live prototype-pollution payload

The guard against __proto__ works by rebuilding the output from pattern keys. Any leaf that returns its input by reference skips that rebuild, so the attacker's own __proto__ key — which JSON.parse creates as a real own property — travels intact through the sanitizer and into whatever the application does next.

const clean = sanitize({ data: any })(JSON.parse('{"data":{"__proto__":{"isAdmin":true}}}'))
Object.keys(clean.data)          // [ "__proto__" ]   ← survived sanitization

naiveRecursiveMerge({}, clean.data)
;({}).isAdmin                    // true              ← Object.prototype polluted globally

Confirmed for any, Object, unknown, NOT(…), someEnsure, each(any), OR(String, any), and every value under OBJECT(any). One correction from writing the tests: OBJECT rebuilds its own key set, so the top level of its output is clean — it is the values underneath, which go through any untouched, that keep their own __proto__. The control behaves correctly — a fully specified nested pattern strips it:

sanitize({ data: { x: Number } })(JSON.parse('{"data":{"x":1,"__proto__":{"p":1}}}'))
// { data: { x: 1 } }   ← clean

This is what makes the library's headline claim conditional in a way nothing documents: it holds only when every leaf is a concrete pattern. Object is the sharpest edge, because it reads as "this must be an object" but is a pure passthrough that also accepts arrays and functions.

const inp = JSON.parse('{"settings":[1,2]}')
sanitize({ settings: Object })(inp).settings === inp.settings   // true
typeof sanitize(Object)(function hack() {})                     // "function"
Reach
Plain JSON body, wherever a permissive leaf is used
Impact
Global Object.prototype pollution once the value meets any merge/extend helper

SA-04High

A key-transforming key pattern walks straight past the poisoning guard

OBJECT.matches checks out[key] using the raw key but writes to out[this.saniKey(key)] using the transformed one. Any key pattern that changes the string — lowercasing, trimming, stripping a prefix — moves the write out from under its own guard.

const against = sanitize(new OBJECT(any, k => k.toLowerCase()))

const out = against(JSON.parse('{"__PROTO__":{"role":"admin"},"role":"user"}'))
Object.hasOwn(out, "role")   // false   ← the client's actual value was dropped
out.role                     // "admin" ← read from the prototype the attacker installed

So the attacker does not merely add a property; they replace one, and the substituted value is invisible to Object.keys, hasOwn and JSON.stringify while being perfectly visible to out.role. Sending {"__PROTO__": null} forces a null-prototype output instead. A prefix-stripping key pattern gives the same result with a lowercase payload:

sanitize(new OBJECT(any, new AND(String, k => k.slice(5))))(
  JSON.parse('{"user___proto__":{"isAdmin":true},"user_name":"bob"}')
).isAdmin                    // true

An identity key pattern (the default) is safe: out["__proto__"] resolves to Object.prototype, so the guard fires. This stays local to the output object — I could not reach the global Object.prototype through it.

Reach
Plain JSON body, wherever a normalising key pattern is used
Note
OBJECT is not documented in the README at all
SA-05High

The result cache is keyed on the input object alone, never on the pattern

Two different patterns applied to the same input object within one call share a result: the second pattern never runs. Where SA-01 is about a failed branch, this is the same cache misfiring on success.

const shared = { role: "admin", extra: "leak" }
sanitize({ a: new OBJECT(any), b: { role: new CONST("guest") } })({ a: shared, b: shared })
// { a: {role:"admin", extra:"leak"}, b: {role:"admin", extra:"leak"} }
//                                     ↑ CONST("guest") never ran, "extra" never stripped

// same across await, with one promise used twice
const P = Promise.resolve({ x: "s" })
await sanitize({ one: new AWAITED({x:String}), two: new AWAITED({x:String, extra:Number}) })({one:P, two:P}).two
// { x: "s" }   ← `extra` is required and simply absent

JSON.parse never produces shared references, so this needs a format that does: YAML anchors, msgpack or BSON with references, circ-json, structured clone, ORM models, or ordinary internal code passing one object into two fields.

Root causeThe cache exists for cycle handling, but a cycle is the same pattern revisiting an object. Keying on input identity alone conflates that with a different pattern seeing it.
SA-06Medium

A pattern loaded from JSON emits an output that is itself a pollution gadget

Pattern keys are trusted implicitly. Because out has a null prototype while it is being filled, a pattern key named __proto__ creates a real own property that survives the closing setPrototypeOf — turning the sanitizer's output into a payload.

const out = sanitize(JSON.parse('{"__proto__":{"isAdmin":false}}'))(
                     JSON.parse('{"__proto__":{"isAdmin":true}}'))
Object.hasOwn(out, "__proto__")   // true — enumerable, writable own property
naiveRecursiveMerge({}, out); ({}).isAdmin   // true

Object literals cannot express this ({"__proto__": x} sets the prototype instead), so it takes a schema built from JSON.parse, Object.create(null), or dynamic keys — which is precisely how schema-registry and multi-tenant setups build patterns.

SA-07Medium

Existing prototype pollution is copied into every sanitized output

for (const key in pattern) walks inherited keys, so a polluted Object.prototype silently adds phantom keys to every pattern compiled afterwards. A library whose purpose is defending against prototype poisoning amplifies it instead.

Object.prototype.LEAK = "evil"
sanitize({ a: String })(JSON.parse('{"a":"x"}'))
// { a: "x", LEAK: "evil" }   ← injected into every response

Object.prototype.INJ = Number
sanitize({ a: String })(JSON.parse('{"a":"x"}'))
// throws: Regarding "INJ": Input is not a number   ← every request now fails

Two limits worth recording: it is compile-time only (the key maps are snapshotted by sanitize(), so a validator built before the pollution is unaffected), and the input's prototype does not leak values — the Object.hasOwn guard on the read path holds correctly.

Root causefor…in over the pattern object. Object.keys would be equivalent for every legitimate pattern.
SA-08High

CONST throws a string, so every error-decorating caller crashes

CONST.matches throws a template literal rather than an Error. Every caller that prefixes context does e.message = …, which in strict mode (both shipped builds) is a TypeError on a primitive. CONST is therefore unusable everywhere except bare, or inside a combinator that swallows the crash.

sanitize({ kind: new CONST("a") })(JSON.parse('{"kind":"b"}'))
// TypeError: Cannot create property 'message' on string 'Expected a, got b'
sanitize(new CONST("a"), "my message")("b")   // same TypeError
sanitize(each(new CONST("a")))(["b"])         // same TypeError
sanitize(new CONST("a"))("b")                 // throws the bare string

It fails closed, but the request becomes a 500 with the diagnostic destroyed rather than a 400 explaining the problem. It also silently degrades SA-01: inside an OR, the TypeError is caught like any other failure.

SA-09Medium

An unsupported pattern value fails with an unrelated TypeError

sanitizeRec has no fallback branch, so against stays undefined and the next line dereferences it. A typo, a missing import, or a stray trailing value produces an error naming an internal symbol.

sanitize({ name: String, age: undefined })
// TypeError: Cannot read properties of undefined (reading 'Symbol(fromInstance)')

Same for null, bigint and symbol patterns. This is the class of bug you flagged: it should be an explicit throw new Error("Unsupported pattern: …") naming the offending key.

SA-10Medium

OBJECT silently deletes any key that shares a name with Object.prototype

The poisoning guard is if (out[key] !== undefined) continue, and out is a plain object — so the check consults its prototype chain and skips a dozen perfectly ordinary key names. No error, in soft mode or otherwise.

sanitize(new OBJECT(any))(JSON.parse(
  '{"constructor":"c","toString":"t","valueOf":"v","hasOwnProperty":"h","normal":"n"}'))
// { normal: "n" }   ← four keys silently gone

OBJECT is precisely the matcher for user-supplied dictionaries — i18n keys, tag maps, form field names — so this is live data loss. A transforming key pattern also collapses colliding keys, last write winning, equally silently.

SA-11High

A function validator is silently reinterpreted as an instanceof check

isConstructor(f) is f.prototype !== undefined, which is true for every function declaration and false for arrows, async functions, bound functions and shorthand methods. The README only ever shows arrows, so the trap is invisible until someone converts one.

function fnValidator(x) { if (typeof x !== "string") throw new Error("nope"); return x }

sanitize(fnValidator)("hi")
// Error: Input is not an instance of fnValidator   ← never calls the function

sanitize(new NOT(fnValidator))("hi")   // "hi"  ← FAIL-OPEN
sanitize(new NOT(fnValidator))(42)     // 42    ← accepts literally everything
sanitize(new NOT(x => { … }))("hi")    // throws, correctly (arrow control)

Standalone it fails closed and loudly. Under NOT it inverts into a validator that can never reject anything — and changing const f = x => … to function f(x) { … } is the kind of edit nobody reviews.

SA-12Medium

regex() never checks that the input is a string

RegExp.prototype.test coerces its argument, so non-strings match and are returned unchanged, while the TypeScript signature claims (input: string) => string.

sanitize(regex(/^\d+$/))(123)                          // 123   (a number)
sanitize(regex(/^\d+$/))(["123"])                      // ["123"] (an array)
sanitize({ t: regex(/^tr/) })(JSON.parse('{"t":true}')) // { t: true }

The array case is the dangerous one: ?id[]=123 through any standard query parser yields ["123"], which passes a digits-only regex and arrives downstream as an array — the classic route into NoSQL operator injection. Composing as new AND(String, regex(…)) fixes it, but nothing signals that you must.

SA-13Medium

each() skips array holes entirely

Array.prototype.map does not visit holes, so they are never validated and pass through into the output.

sanitize(each(String))(["a", , "c"])                   // [ 'a', <1 empty>, 'c' ]
sanitize(each(new CONST("only-this")))(new Array(5))   // [ <5 empty> ]  — passes
sanitize(each(0))([undefined, 5])                      // [0, 5]  — control, defaults applied

Not reachable from JSON.parse (JSON has no holes), so this needs a hand-built array, a CSV/msgpack importer, or a query parser with sparse-array support. Worth noting that a downstream reader sees undefined where the type says string.

SA-14Medium

addPattern changes validators that were compiled long before

OBJECT.init memoises itself; Combinator.init does not. So a combinator instance is re-initialised by every sanitize() that references it, and because matches reads this.sanis at call time, that re-initialisation retroactively rewrites already-built validators.

const o = new OR(String)
const against = sanitize(o)

against(5)          // throws — correct
o.addPattern(Number)
against(5)          // still throws — the mutation appears to be ignored…

sanitize(o)         // …until some unrelated module compiles its own validator
against(5)          // 5   ← the original validator's behaviour just changed

Both halves are surprising: the mutation looks like a no-op, then lands later at a distance. The natural recursive-schema idiom is also silently non-recursive, because each() calls sanitize() eagerly:

node.addPattern({ children: each(node) })   // compiles, never actually recurses
node.addPattern(node)                       // RangeError at sanitize() time
SA-16Medium

numberLike* inherits every quirk of unary +

The check is !isNaN(+input), which is far broader than "looks like a number":

sanitize(numberLikePattern)("0x1f")      // 31
sanitize(numberLikePattern)("0b101")     // 5
sanitize(numberLikePattern)("0o17")      // 15
sanitize(numberLikePattern)("Infinity")  // Infinity
sanitize(numberLikePattern)("1e400")     // Infinity
sanitize(numberLikePattern)("   ")       // 0          ← whitespace-only
sanitize(numberLikePattern)("  12  ")    // 12

numberLikeStringPattern compounds it by design — it preserves the raw text, so a "validated numberlike string" can be " 12 ", "0x1f", "+1" or "Infinity". If those become cache keys, IDs, or filenames, two different strings denote the same number and vice versa.

SA-20Medium

Shared input references become shared, mutable output objects

A consequence of the same cache as SA-05: two fields that referenced one input object come back referencing one output object, so writing through one is visible through the other.

const shared = { x: "1" }
const out = sanitize({ a: { x: String }, b: { x: String } })({ a: shared, b: shared })
out.a.x = "MUTATED"
out.b.x           // "MUTATED"     out.a === out.b

Sanitized output reads as a fresh, owned copy; here it is a graph with aliasing that mirrors the attacker's input structure.

SA-23Medium

The typed output is unusable, so consumers reach for as any

An object pattern's output type has no accessible properties:

const r = sanitize({ name: String, age: Number })(body)
const x: string = r.name
// TS2339: Property 'name' does not exist on type
//         'SanitizeNestedOb<{ name: StringConstructor; age: NumberConstructor; }, true>'

Five cases reproduce: a flat object pattern, a nested one, the README's headline example, a union's discriminant (so the idiomatic switch (result.kind) after sanitizing is unavailable — the one place the types would earn their keep), and an AND pipeline ending in an object pattern. The only ergonomic response is as any on the result, which discards the type-level guarantee at exactly the boundary where it is supposed to hold.

Corrected since the first pass. strictNullChecks is the switch, not strict as a whole. It is on in every strict: true project — the default for new consumers — and then property access is a hard TS2339. With it off, the conditional types collapse to any instead, so the output has no type safety at all: quieter, not better. Either way the guarantee is not delivered.

Also corrected: the other suspected type failures do not reproduce, and are recorded as checked-and-clean so nobody re-investigates them — each() nested in an object pattern, each(each(…)), each() inside AND; regex(), stringStartsWith(), numberLikePattern, nonEmptyStringPattern, numericRange() and ensure() used as patterns; typed function patterns such as sanitize((input: number) => input); indexing an each() or OBJECT() result; reading an optional-only key.

Verified against the declarations emitted by tsconfig.prod.esm.json on TypeScript 5.0.4, the version in devDependencies.

SA-32High

Five sanitize() calls in one file crash the TypeScript compiler

Found while writing the test coverage. Type-checking this file does not fail — it aborts:

const shapes: [string, () => unknown][] = [
  ["happy path",    () => sanitize({ a: String })(body)],
  ["union",         () => sanitize(new OR({ a: String, b: Number }, { a: String }))(body)],
  ["AND after NOT", () => sanitize(new AND(new NOT({ z: Number }), { a: String }))(body)],
  ["soft OBJECT",   () => sanitize(new OBJECT(Number, true))(body)],
  ["nested",        () => sanitize({ n: { a: String } })(body)],
]

// RangeError: Maximum call stack size exceeded
// no error code, no file, no line — just a compiler stack trace

No single pattern is the culprit; each compiles fine alone. Sanitized, ParseIfCombinator and DeepOBJECT are simply expensive enough that inference across a handful of distinct call sites exhausts tsc's stack. Bisecting the audit test file put the threshold at six un-erased call sites; the trimmed fixture reproduces with five.

Five sanitizers is an ordinary amount for one route file, so this is reachable by writing normal code, and it is close to undiagnosable from a consumer's seat — there is nothing to search for. The only workaround is to erase the sanitizer's return type, which is the same as any that SA-23 already forces. Ranked High for that reason: unlike the rest of SA-23 it is not an ergonomic complaint, it is a hard build failure.

SA-15Low

A self-referential pattern blows the stack at compile time

knownPatternObjects.set(pattern, against) runs after the recursive descent instead of before, so the cache that exists to handle pattern cycles never gets the chance to.

const p = { name: String }; p.self = p
sanitize(p)                                   // RangeError: Maximum call stack size exceeded

const a = { name: String }, b = { a }; a.b = b
sanitize(a)                                   // RangeError (mutual recursion)

Registering the placeholder before recursing is the same one-line reordering as SA-01, in the pattern cache rather than the input cache.

SA-17Low

regex() writes to the RegExp the caller handed it

regex.lastIndex = 0 mutates the caller's object, and test() then advances it again on a global regex. A regex shared with any other part of the application has its iteration state clobbered by an incoming request.

const shared = /a/g; shared.lastIndex = 7
sanitize(regex(shared))("aaaa")
shared.lastIndex   // 1   ← the other consumer's cursor is gone

The warning that fires for g/y flags names the risk but does not prevent it; cloning the regex would.

SA-18Low

Helpers raise TypeError where a validation error belongs

sanitize({ p: stringStartsWith("a") })({ p: 5 })
// TypeError: Regarding "p": input.startsWith is not a function
sanitize({ p: stringStartsWith("a") })({ p: null })
// TypeError: Cannot read properties of null

Fail-closed, but an application that maps validation errors to 400 and everything else to 500 returns the wrong status and logs the wrong severity for an ordinary bad request. Inside an OR it is simply swallowed (see SA-29).

SA-19Low

Cross-realm values and thenables are rejected

The plain-object test compares getPrototypeOf(input).constructor === Object, each uses instanceof Array, and AWAITED uses instanceof Promise — all realm-bound.

const foreign = vm.runInContext('({a:"b"})', ctx)
sanitize({ a: String })(foreign)          // Error: Input is not a plain object
sanitize(each(String))(vm.runInContext('["a"]', ctx))
// Error: Input is not an instance of Array
sanitize(new AWAITED(String))({ then(r) { r("hi") } })
// Error: Input is not an instance of Promise

Matters for vm sandboxes, iframes (there is a web build), and any library returning a non-native thenable. Array.isArray and a duck-typed then check are the realm-safe equivalents.

Worth recording alongside: the plain-object test is a constructor identity check, not a prototype identity check, so Object.create({ constructor: Object, isAdmin: true }) passes it — and OBJECT's for…in then copies the inherited keys into the output. Object patterns are unaffected (their hasOwn guard holds). Not reachable from JSON, but it is the guard doing less than it appears to.

SA-21Low

AND is a pipeline, documented as an intersection

"Passes if all of them pass" reads as an intersection, but each stage receives the previous stage's filtered output — so an intersection of two object patterns can never succeed.

sanitize(new AND({ a: String }, { b: Number }))(JSON.parse('{"a":"x","b":1}'))
// Error: Regarding "b": Input is not a number   ← b was stripped by stage 1

The pipeline behaviour is the useful one and the examples rely on it; the prose is what needs to change.

SA-22Low

{a, "a?"} silently means "required and optional"

Both keys normalise to a but land in different maps, so both run and the optional one overwrites. A plausible merge conflict or copy-paste produces a field that must satisfy two patterns at once, reported as a confusing failure on a value that satisfies the one you can see.

sanitize({ a: String, "a?": Number })({ a: "str" })
// Error: Regarding "a": Input is not a number

Also worth documenting: a key of "?" resolves to the optional empty-string key "".

SA-24Low

No README combinator example runs as written

Every example calls the combinators as functions, but they are classes:

OR(Number, String)
// TypeError: Class constructor OR cannot be invoked without 'new'

const { sanitize } = require("sanitize-against")
// undefined — the CJS build exports `default`, not `sanitize`

Either add function wrappers and a named sanitize export, or fix the docs. The first option is friendlier and keeps the README honest.

SA-25Low

A stray local file shipped inside the npm tarball

sanitize-against@1.8.0 contains seven files, and one of them is sercurity analysis.txt — your own notes for this audit. It is not in git, so .npmignore simply never learned about it.

npm pack sanitize-against@1.8.0 && tar tzf sanitize-against-1.8.0.tgz
package/app/dist/cjs/sanitizeAgainst.js
package/app/dist/esm/sanitizeAgainst.mjs
package/app/dist/{cjs,esm}/sanitizeAgainst.d.ts
package/package.json
package/README.md
package/sercurity analysis.txt          ← not in the repository

Nothing sensitive this time. The structural point is that .npmignore is deny-by-omission: anything you leave in the working directory ships. A "files" allowlist in package.json inverts that, and npm publish --dry-run shows the manifest before it goes out.

Near misses

Not exploitable as the code stands — I tried. Each is one plausible patch away from becoming one of the findings above.

SA-26Near miss

Async cache state is nulled rather than restored

AWAITED.matches saves knownInputObjects, restores it inside the then, then assigns null instead of the value it saved. OR's awaited path does not restore at all when every branch fails.

I could not break it: 400 interleaved AWAITED sanitizations, 300 nested-AWAITED jobs, and 600 mixed jobs with rejections and shared object identities produced zero mismatches and zero spurious errors. Every callback reassigns the global before reading it, and the microtask model prevents interleaving inside the synchronous window that matters.

It survives on a coincidence of scheduling. A module-level mutable holding per-call state is the shape that breaks the moment anything reads it on a path that does not write it first — which is what a new combinator, or a for await loop, would plausibly add.

SA-27Near miss

The poisoning guard depends on the very inheritance it guards against

OBJECT's out[key] !== undefined only catches __proto__, constructor and friends because out is {} and inherits them. Hardening it to Object.create(null) — the obvious, correct-looking change, and the one the object-pattern branch already makes — silently removes the guard.

The two mechanisms are load-bearing for each other in a way nothing in the code says out loud. Whoever makes that edit will have the tests pass (SA-10's silent key dropping disappears, which looks like a fix) while re-opening SA-04 for the default key pattern.

An explicit key denylist, or building on a null-prototype object and rejecting dangerous keys by name, removes the coupling.

SA-28Near miss

Every property is read twice

input[key] === undefined || Object.hasOwn(input, key) ? input[key] : undefined evaluates input[key] on both sides.

let n = 0
const inp = { get a() { return n++ === 0 ? "safe" : "EVIL" } }
sanitize({ a: String })(inp)   // { a: "EVIL" }  — the second read is what is stored

Currently benign, because the stored value is the validated one. It becomes a genuine time-of-check/time-of-use bug the moment anyone refactors it into a variable used for the check and re-reads for the value, or the reverse — and the natural "let's not read twice" cleanup can land on either side. Getters with side effects also run twice today.

SA-29Near miss

catch {} swallows programming errors, not just failures

This is SA-02's root cause stated as a design property. OR, NOT, matches() and soft OBJECT treat RangeError, TypeError and any future internal bug as "did not match".

Beyond the exploit, it means every bug in a validator is invisible: a typo in a custom pattern makes the branch quietly not match rather than surfacing. A dedicated ValidationError class, with anything else rethrown, would close SA-02 and turn a whole category of silent misbehaviour into loud failures.

SA-30Near miss

Attacker code runs while formatting error messages

CONST interpolates the input into its message, which invokes an attacker-controlled toString on the failure path:

sanitize(new CONST("user"))({ toString() { throw new Error("boom from toString") } })
// Error: boom from toString   ← attacker chooses the error the caller sees
sanitize(new CONST("user"))("<script>alert(1)</script>")
// "Expected user, got <script>alert(1)</script>"

Two latent edges: raw input reaching logs or a response body (log injection, reflected content), and error-path code running attacker-supplied functions. Both are contained today because the throw still propagates.

SA-31Near miss

The output prototype is repaired last, not set first

Output objects are built as Object.create(null) and given Object.prototype by a setPrototypeOf on the final line. Every early exit therefore yields a null-prototype object — which is how SA-01's residue escapes with no toString.

The null prototype during construction is also load-bearing for SA-06: it is why a __proto__ pattern key becomes a real own property instead of a prototype assignment. Constructing with Object.create(Object.prototype) and explicitly handling dangerous keys would make the invariant hold at every exit rather than only the successful one.

What I could not break

Negative results, so they do not get re-investigated later:

  • No global pollution during sanitization itself. Key-transform writes, colliding transformed keys, deep-mode nesting, a key pattern returning __proto__ for every key, constructor-named keys — all only re-point the local output's prototype. Object.prototype gained no own property in any variant. Every global pollution finding here needs a downstream merge.
  • The hasOwn read guard holds. Inherited properties on the input never reach the output through an object pattern, including when the input's prototype is spoofed to pass the plain-object check.
  • No async cross-call contamination. See SA-26 — 1,300 concurrent and nested jobs, zero mismatches.
  • No super-linear complexity. OBJECT over 100,000 keys: 45 ms. each(String) over 400,000 elements: 37 ms. Nested OR/AND to depth 16: flat. Error-message rebuilding at pattern depth 1,600: 2.6 ms. The only resource issue is the stack overflow, and it matters as the fail-open in SA-02 rather than as a denial of service.

If you fix nothing else

Three changes retire most of this list:

  • Populate before caching, or key the cache on (pattern, input) rather than input. Retires SA-01, SA-05, SA-20, and the null-prototype leak in SA-31; the same reordering in knownPatternObjects retires SA-15.
  • Throw a distinguishable ValidationError and rethrow everything else from every catch. Retires SA-02, fixes SA-08 on the way, and turns SA-29 and SA-18 into loud failures.
  • Say plainly which leaves are pass-through — any, Object, unknown, NOT, someEnsure — and that the __proto__ guarantee only covers values a concrete pattern rebuilds. Or strip __proto__ from returned objects on the way out, which would make the README's claim unconditional.

All findings reproduced against the published sanitize-against@1.8.0 build (app/dist/esm/sanitizeAgainst.mjs) on Node 22.22.2, not only against the TypeScript source. The repository's own suite passed 115/115 throughout, so none of this was caught before. The deep-recursion findings need node --stack-size left at its default to reproduce the stated thresholds.
